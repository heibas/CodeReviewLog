# 代码评审报告

## 1. 总体结论

**变更目的**：新增独立的微信模板消息通知入口 `WeChatNotifier`，用于在代码评审完成后，从环境变量读取微信凭据、读取 Git 提交元数据，获取 `access_token` 并推送包含评审报告链接的模板消息；同时附带针对配置解析、URL 校验、消息构建、敏感信息脱敏的单元测试。

**主要风险**：
- `main` 中使用 `new File(".")` 读取 Git 元数据，对工作目录有强隐式依赖，在 CI 环境中容易读错仓库或直接失败。
- HTTP 层（`requestAccessToken` / `sendTemplateMessage`）完全无测试覆盖，异常封装存在消息重复前缀的小瑕疵。
- 微信 secret 通过 URL query 传输（受限于微信 API 设计），需依赖脱敏机制兜底，而 `redact` 的覆盖场景有限。

**是否建议合入**：**建议合入**，但建议先修复“高”级别问题（工作目录依赖），其余中低级别问题可跟进修复。整体代码质量较好，安全意识（凭据仅从环境变量读取、异常脱敏）到位。

---

## 2. 问题清单

### 阻断
无阻断性问题。

### 高

**H1. `WeChatNotifier.java` — `main` 方法中 `new File(".")` 隐式依赖工作目录**
- **位置**：`main` 方法 `GitCommitMetadataReader.readHead(new File("."))`
- **问题**：Git 仓库路径硬编码为当前工作目录。在 CI/CD 中，Java 进程的启动目录未必是仓库根目录，会导致读取失败或读取到错误的提交信息，且失败现象与代码本身无关，排查困难。
- **影响**：通知中携带错误的 commit 信息，或整个通知流程在非预期目录下运行时失败。
- **修复建议**：将仓库路径提取为第二个可选命令行参数或环境变量（如 `GIT_REPO_DIR`），缺省再回退到 `"."`，并在失败时输出解析后的绝对路径便于诊断。

### 中

**M1. `WeChatNotifier.java` — `requestAccessToken` 异常消息前缀重复**
- **位置**：`requestAccessToken` 内 `throw new IOException("获取微信 access_token 失败：响应中没有 access_token")` 会被外层 `catch` 再次经 `sanitizedFailure("获取微信 access_token 失败", ...)` 包装。
- **问题**：最终消息变为 `获取微信 access_token 失败：获取微信 access_token 失败：响应中没有 access_token`，前缀重复。
- **影响**：日志可读性下降，无功能影响。
- **修复建议**：内部抛出的业务异常使用不带操作前缀的消息（如 `"响应中没有 access_token"`），由外层统一添加前缀。

**M2. `WeChatNotifier.java` — `validateReportUrl` 通过消息前缀匹配区分异常来源，逻辑脆弱**
- **位置**：`validateReportUrl` 的 `catch (IllegalArgumentException e)` 块
- **问题**：用 `e.getMessage().startsWith("评审报告 URL")` 区分"自定义异常"与 `URI.create` 抛出的解析异常，一旦消息文案调整，自定义异常会被错误地包装成"格式不正确"，丢失原始语义。
- **影响**：维护期易出现错误提示与真实原因不符，误导调用方。
- **修复建议**：将 scheme/host 校验移出 `try` 块，仅在 `URI.create` 处捕获解析异常：

```java
URI uri;
try {
    uri = URI.create(reportUrl.trim());
} catch (IllegalArgumentException e) {
    throw new IllegalArgumentException("评审报告 URL 格式不正确");
}
if (!"https".equalsIgnoreCase(uri.getScheme()) || uri.getHost() == null) {
    throw new IllegalArgumentException("评审报告 URL 必须是有效的 HTTPS 地址");
}
return uri.toString();
```

**M3. `WeChatNotifier.java` — HTTP 响应体为空时 `JSON.parseObject` 返回 `null`，引发 NPE**
- **位置**：`requestAccessToken` / `sendTemplateMessage` 中 `JSON.parseObject(readResponse(...))` 之后直接调用 `ensureSuccess(response, ...)`。
- **问题**：若网关或代理返回 2xx 但空 body（异常情况下可能发生），`response` 为 `null`，`response.getIntValue` 抛出 NPE；虽然会被 `catch RuntimeException` 捕获并脱敏包装，但错误信息变为 `NullPointerException`，丢失真实原因。
- **影响**：极端网络异常下排障困难。
- **修复建议**：解析后判空，为 `null` 时抛出带操作名的 `IOException`（如 `"响应不是有效 JSON"`）。

### 低

**L1. `WeChatNotifier.java` — `commitSummary` 按 UTF-16 码元截断，可能截断代理对（emoji 等）**
- **位置**：`firstLine.substring(0, maxLength - 1)`
- **问题**：若第 79 个 char 恰好是高代理项，会产生孤立代理字符，微信侧可能显示为乱码。
- **影响**：极低概率的展示瑕疵。
- **修复建议**：使用 `codePoint` 方式截断，或截断后校验并丢弃末尾孤立代理字符。

**L2. `WeChatNotifier.java` — 无网络重试与令牌缓存说明**
- **问题**：一次性 CLI 场景下可接受，但瞬时网络抖动会直接导致整个通知失败，且无任何重试。
- **修复建议**：可增加 1~2 次带退避的轻量重试；或在文档中明确"失败即终止，由上游 CI 重试"的设计决策。

**L3. `WeChatNotifier.java` — `redact` 的正则仅覆盖 `access_token=xxx` 形式**
- **问题**：如 secret 以 JSON 形式（`"access_token":"xxx"`）出现在错误消息中，正则无法命中，只能依赖后续按字面量替换 secret 值兜底——前提是调用方记得把该值传入 `secrets`。
- **修复建议**：当前调用点均已传入相关 secret，风险可控；建议在 `redact` 的 Javadoc 中明确约定"所有可能出现在消息中的敏感值必须作为 `secrets` 参数传入"。

## 3. 值得肯定之处

1. **安全意识突出**：凭据仅从环境变量读取；类注释明确"日志和异常不得包含 secret 或 access_token"；`redact`/`sanitizedFailure` 对所有出口异常做脱敏，且使用 `String.replace`（字面量）而非正则替换 secret，避免正则注入问题。
2. **输入校验严格**：报告 URL 强制 HTTPS 且校验 host，避免明文凭据外发风险；环境变量缺失时 fail-fast 并指出具体变量名。
3. **可测试性设计良好**：`fromEnvironment` 接受 `Map` 而非直接读 `System.getenv()`，`buildTemplateMessage`、`commitSummary`、`redact` 均为纯函数式的 `static` 方法，便于单测。
4. **测试质量较高**：覆盖了配置读取、缺参、非法 URL、消息结构、中文提交摘要截断、脱敏等关键路径；断言精确（如截断后长度恰好 80、以 `…` 结尾）。
5. **细节处理到位**：HTTP 超时显式设置（连接 10s / 读 15s）、错误流读取、`finally` 中断开连接、提交摘要折叠空白并截断，均体现了对边界情况的考虑。

## 4. 后续建议

1. **补齐 HTTP 层测试**：使用 `MockWebServer`（OkHttp）或 JDK 内置 `com.sun.net.httpserver.HttpServer` 启动本地服务，覆盖以下场景：
   - 微信返回 `errcode != 0` 时异常消息已脱敏且包含错误码；
   - HTTP 4xx/5xx 时异常不包含响应 body 中的敏感信息；
   - 空响应体 / 非 JSON 响应的行为（配合 M3 修复）。
2. **修复 H1 后补集成测试**：在临时目录初始化一个 Git 仓库，验证 `main` 在指定仓库路径下能正确读取提交元数据（可将网络调用抽为可替换的函数接口以便注入）。
3. **增加端到端冒烟开关**：提供 `--dry-run` 参数，仅打印构建出的模板消息（脱敏后）而不实际发送，便于在 CI 中验证配置与消息格式。
4. **文档化运维约束**：在 README 或类 Javadoc 中说明：`WECHAT_TO_USER` 对应的用户需已关注公众号；模板需包含 `first/keyword1~3/remark` 字段且与微信后台模板结构一致；`access_token` 未做缓存（单进程一次性运行无影响，若未来改为常驻服务需引入缓存与刷新）。
5. **考虑网络重试**：对 `requestAccessToken`/`sendTemplateMessage` 增加最多 2 次指数退避重试，降低 CI 中因瞬时抖动导致的通知失败率（对应 L2）。
